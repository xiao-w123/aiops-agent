# 智能运维 Agent —— 毕业设计升级方案

> 目标：把当前"工程 Demo"升级为"有实验章节、有技术贡献点、工作量可量化"的本科毕业设计。

## 0. 现状诊断

### 已有优势
- 选题好：智能运维 Agent 属于当前热点方向，问题域真实。
- 闭环完整：RAG 建库 → Agent 编排 → FastAPI → Web 前端 → 评测脚本全链路打通。
- 已有评测意识：`eval.py` 采用"期望工具集 + 期望关键词"双指标。
- 已有对照雏形：`agent_v1.py`（无 RAG）与 `agent_v2.py`（含 RAG）分离，是全文最有价值的伏笔。

### 必须解决的问题
| 问题 | 影响 |
| :--- | :--- |
| `tools.py` 全为硬编码 mock，任何 service 返回相同数据 | 评测结果无证明力，测试集与 mock 互相"喂"答案；答辩易被质疑数据造假 |
| 核心 ReAct 循环由 `create_agent` 一行完成 | "自己做了什么"不清晰，缺技术贡献点 |
| 测试集仅 5 条，无消融/无对照/无重复实验 | 统计上说明不了任何问题 |
| RAG 过于基础：3 篇文档、固定 chunk 300、k=2 | 检索质量不构成问题，实验章节无内容可写 |
| 无流式输出、无多轮记忆、无依赖清单 | 工程完整性偏弱，演示观感差 |
| README 声称使用 LangGraph，代码中未使用 | 材料与实现不符，论文中属硬伤 |

## 1. 核心改造主线

> 从"我做了个智能运维 Agent"
> 升级为"我提出并验证了一种面向运维场景的检索增强 Agent 方案，相比基线在 X 指标上提升 Y%"。

评审关注三点：工作量可量化、有对照、结论有数据支撑。

## 阶段 1（约 1 周）：可信的评测基础设施【地基，必做】

**前置理由**：后续所有实验均依赖此处的数字产出。地基不牢，任何实验结论都会被质疑。

### 1.1 重写 `tools.py` 为确定性仿真运维环境
- 不同 service 返回真正不同的指标、日志、发布记录。
- 指标含时间序列；日志含噪声（无关 INFO 日志干扰检索）。
- 发布记录含干扰版本（与故障无关的版本）。
- **关键要求**：故障根因不可从单一工具返回值直接读出，必须交叉推理
  （例："监控显示 CPU 升高但内存正常，响应时间同步劣化"）。
- 保持确定性（固定随机种子），保证实验可复现。

### 1.2 构建分层测试集（100–150 条）
按能力分层标注，每层 20–30 条：

| 层级 | 能力 | 说明 |
| :--- | :--- | :--- |
| L1 | 单工具事实查询 | "order-service 昨晚 CPU 多少" |
| L2 | 多工具联合推理 | 需组合监控 + 日志 + 发布记录 |
| L3 | 根因定位 | 输出正确根因，需交叉证据链 |
| L4 | 历史经验迁移 | 需检索历史故障报告并正确类比 |
| L5 | 边界与拒答 | 无故障时不应编造根因 |

每条标注：ground truth 根因、期望工具集、关键证据链、难度标签。

### 1.3 升级 `eval.py` 为评测框架
- 多组对照跑批（baseline / v1 / v2 / 优化版）。
- 每组重复 N 次取均值与方差（LLM 输出有随机性，单次为单点噪声）。
- 错误分类归因：工具漏调 / 工具错调 / 多轮不收敛 / 幻觉编造证据 / 根因错误。
- 自动导出 Markdown 表格与图表，可直接粘贴进论文。

**阶段 1 产出**：仿真故障场景数据集 + 可复现评测框架（论文中可独立成节："面向评测的故障场景仿真数据集构建"）。

## 阶段 2（约 2 周）：RAG 检索增强【论文最扎实的实验章节】

沿用公认指标与公认 baseline，写作成本低、说服力强。

### 2.1 检索策略对比
- 纯稠密向量检索（当前方案）
- BM25 稀疏检索
- 混合检索（RRF 融合）

### 2.2 切分参数消融
- `chunk_size ∈ {200, 300, 500, 800}`
- `overlap ∈ {0, 50, 100}`

### 2.3 重排序
- 引入 `bge-reranker`，召回后重排
- 对比 `k = 1 / 2 / 3 / 5`

### 2.4 评测指标
- 检索层：Recall@k、MRR、nDCG
- 端到端：根因定位准确率、证据链完整率

### 2.5 知识库扩容（重要）
当前 3 篇文档 + `k=2`，本质上等同于"把文档直接塞进提示词"。
扩到 20–30 篇故障报告后，检索质量才成为真问题，实验才有意义。

### 2.6 进阶：查询改写
将口语化提问改写为检索友好查询再检索。
例："响应变慢" → "连接池耗尽 响应时间飙升 CPU 升高"。

## 阶段 3（约 1 周）：消融与对照【论文核心论据】

### 3.1 主对照（全文最有力的数据）
`agent_v1`（无 RAG） vs `agent_v2`（有 RAG） vs 优化后版本

### 3.2 消融实验表
逐项移除并观察性能下降：
- 移除历史故障检索
- 移除重排序
- 移除查询改写

### 3.3 框架对照
- ReAct 自由循环 vs LangGraph 显式状态机编排
- 指标：工具调用轮数、token 消耗、平均延迟、任务成功率
- 附带修复 README 中"声称使用 LangGraph 但未使用"的不一致

### 3.4 基线对照
无工具调用的纯 LLM（直接提问）作为 lower bound，证明 Agent 架构的必要性。

## 进阶加分项（有余力再做）

### 多 Agent 协作
诊断 Agent + 证据校验 Agent + 报告生成 Agent，Supervisor 模式编排。

### 重点推荐：证据校验 Agent
专职检查"结论中引用的证据是否真的出现在工具返回结果中"，用于抑制幻觉。
- 优点：可量化（幻觉率下降幅度）、思路清晰、贴合前沿工作强调的 evidence-verified 方向。
- 可作为论文的一个独立创新点。
