# 实验结果与结论

本文件记录基于修复后评测框架的实测结果，**包括负面结果**。
论文的实验章节可直接引用，但请以 `results/report_latest.md` 中实际生成的数据为准，
不要手工誊抄。

## 一、实验设置

| 项目 | 配置 |
| :--- | :--- |
| 模型 | DeepSeek deepseek-chat（temperature=0） |
| 检索 | 稠密向量检索，`k=2`，Embedding 为 BAAI/bge-small-zh-v1.5 |
| 测试集 | 30 条，L1-L5 各 6 条 |
| 重复次数 | 3 |
| 并发 | 8 线程 |
| 指标口径 | 均值 ± 标准差，跨重复次数统计 |

对照组设置：

| 配置 | 说明 |
| :--- | :--- |
| 无证据校验（基线） | ReAct + RAG，四工具，无校验环节 |
| 含证据校验（本方案） | 在基线之上叠加证据校验与重答 |

两组共用同一个 Agent 构造路径，**唯一变量是是否挂载证据校验**。

## 二、总体结果

| 指标 | 无证据校验 | 含证据校验 | 变化 |
| :--- | :--- | :--- | :--- |
| 工具调用 F1 | 83.1 ± 1.0 | 83.5 ± 0.5 | +0.4 pp |
| 证据命中率 | 89.4 ± 1.9 | 88.3 ± 0.0 | −1.1 pp |
| 根因定位准确率 | 78.9 ± 3.8 | 71.1 ± 1.9 | **−7.8 pp** |
| 幻觉根因率（越低越好） | 10.0 ± 0.0 | 17.8 ± 1.9 | **+7.8 pp（变差）** |
| 拒答正确率（L5） | 44.4 ± 9.6 | 38.9 ± 9.6 | −5.5 pp |
| 平均耗时 | 6.55 ± 4.76 s | 5.51 ± 0.14 s | −15.9% |

分层明细：

| 层级 | 能力 | 根因准确率（基线） | 根因准确率（校验） | 幻觉率（基线） | 幻觉率（校验） |
| :--- | :--- | :--- | :--- | :--- | :--- |
| L1 | 单工具事实查询 | 100.0% | 100.0% | 0.0% | 0.0% |
| L2 | 多工具联合推理 | 72.2% | 66.7% | 0.0% | 0.0% |
| L3 | 根因定位 | 77.8% | 50.0% | 16.7% | 50.0% |
| L4 | 历史经验迁移 | 100.0% | 100.0% | 0.0% | 0.0% |
| L5 | 边界与拒答 | 44.4% | 38.9% | 33.3% | 38.9% |
| **总体** | — | **78.9%** | **71.1%** | **10.0%** | **17.8%** |

## 三、核心结论：证据校验在本设置下整体无效

**引入证据校验后，根因定位准确率下降 7.8 个百分点，幻觉根因率反而上升 7.8 个百分点。**

且该退步并非只出现在某一层，而是 L2、L3、L5 三层同时变差，
其中 L3（根因定位）从 77.8% 降到 50.0%，是主要损失来源。

因此不能声称证据校验有效。这是一个**负面结果**，需如实报告。

## 四、失败机制分析

### 4.1 校验环节判定过于激进

实测中 30 条用例里有 13 条触发了重答，包括：

- `L1-004`「user-service 的内存使用率是多少？」——**纯查询问题，根本不需要给根因**，
  却被判定为"编造根因"，触发重答。

这说明校验提示词对"何为编造"的界定过宽。

### 4.2 重答提示词把模型引导向过度保守

初版重答提示词中含有一句：

> 如果数据不足以得出根因，就如实说明"证据不足"

后果：模型把**有充分证据支持**的正确诊断改写成了"证据不足"。典型例子：

| 用例 | 重答前（正确） | 重答后（错误） |
| :--- | :--- | :--- |
| L3-003 | "这是一次典型的内存泄漏"（监控 40%→89% + OOM 日志） | "证据不足，无法确定根因" |
| L3-005 | "缓存穿透"（日志 Cache miss rate 95%） | "证据不足，无法定位根因" |
| L3-002 | "缓存穿透导致"（日志 + DB 超时） | "证据不足，无法确定唯一根因" |

**证据本来是充分的，重答却把正确结论抹掉了。** 这是提示词设计缺陷。

### 4.3 修正提示词后结果更差

针对 4.2 修改提示词，明确指示"证据可合理推出即应给出结论，不要因证据是间接的而放弃"，
缩小 L3+L2+L5 范围复测：

| 指标 | 基线 | 修正前校验 | 修正后校验 |
| :--- | :--- | :--- | :--- |
| L3 根因准确率 | 88.9% | 50.0% | 33.3% |
| L3 幻觉根因率 | 11.1% | 50.0% | 66.7% |

修正后**反而更差**。说明问题不只是提示词措辞，而是更根本的：

1. **校验本身也是一次 LLM 调用，同样会出错**，其判定精度不足以支撑"拦截"这一破坏性动作；
2. **"拦截后重写"的代价不对称**：把正确结论改写为"证据不足"是确定性损失，
   而它本应防止的幻觉是概率性收益；
3. **基线本身幻觉率已较低**（总体 10.0%），校验在解决一个并不严重的问题，
   却引入了新的、更大的错误。

### 4.4 校验触发的具体代价

以最终一次评测中的 L3 为例，校验把原本正确的诊断批量改写成了"证据不足"：

| 用例 | 基线（正确） | 校验后（错误） |
| :--- | :--- | :--- |
| L3-002 | 缓存穿透（日志 Cache miss 95% + DB 超时） | 证据不足，无法确定唯一根因 |
| L3-003 | 内存泄漏（监控 40%→89% + OOM） | 证据不足，无法确定根因 |
| L3-004 | 连接未释放（历史故障报告） | 证据不足，无法确定根本原因 |

这三条的证据链本身是完整的，被改写后直接导致 L3 根因准确率从 77.8% 掉到 50.0%。

### 4.5 值得注意的正面发现

基线组在 L4（历史经验迁移）达到 **100.0%** 的根因准确率、
在 L3 达到 **77.8%**，说明 **ReAct + RAG 的基础架构本身是有效的**——
历史故障知识库的引入确实让 Agent 能答出"连接未释放""需用 try-with-resources"
这类只存在于知识库中的细节。

同时，**L5（边界与拒答）是真正的短板**，拒答正确率仅 44.4%：
模型在服务健康时仍倾向于给出一个看起来专业的根因，这才是值得投入优化的方向。

## 五、对后续工作的建议

若要继续该方向，以下路径比"再调提示词"更有希望：

1. **改"拦截重写"为"并列出证据"**。不要覆盖原回答，而是把校验发现的
   证据缺口作为附注输出（"以下结论中 X 缺乏直接数据支撑"），
   由使用者判断。这样即使校验误判也不会破坏正确结论。
2. **只在低置信场景触发校验**。例如仅在"服务指标正常但模型给出了故障根因"时触发，
   而不是对所有回答都校验。这能把触发率从 43% 降到接近真实幻觉率。
3. **用结构化输出替代自由文本判定**。让校验模型以 JSON 返回
   `{"fabricated": bool, "root_cause": str, "missing_evidence": str}`，
   避免 `normalize_verdict` 依赖首行文本解析。
4. **引入独立证据而非再问同一个模型**。例如让校验环节**必须调用工具复核**
   模型引用的关键事实是否真实存在于返回值中，把"自我检查"变成"外部核验"。
5. **换更强的审查模型**。用比被审查模型更强的模型做校验可提升判定质量，
   但需额外成本，并须报告成本-收益。

## 六、方法局限（须在论文中声明）

1. **仿真数据**。全部实验在确定性仿真运维环境（`simulator.py`）中进行。
   真实生产故障数据涉及企业敏感信息且难以复现，本文关注的是
   不同策略的**相对性能**差异，而非绝对性能。
2. **测试集规模**。30 条用例、每层 6 条，样本量偏小，
   分层指标的标准差较大（如 L3 耗时为 16.89 ± 20.13），
   部分差异不具统计显著性。
3. **规则判分**。根因与拒答判定基于短语组匹配与子句级语气分析，
   属启发式方法，存在误判可能（详见 `评测指标说明.md`）。
4. **温度设置为 0 仍非完全确定**。实测同一用例在不同重复间存在输出差异，
   推测来自服务端采样或工具调用序列差异，方差已在报告中体现。
5. **单一模型**。仅评测了 deepseek-chat，结论未必可推广到其他模型。

## 七、答辩问答准备

以下是本项目的实际弱点与建议答法。**建议提前想清楚，不要临场编**。

### Q1：你的证据校验没有效果，那你的工作量体现在哪？

这是最可能被问到、也最关键的一问。建议按三层回答：

1. **基础设施层**：构建了确定性仿真运维环境（4 个服务、故障状态互不相同、
   指标为时间序列、证据需交叉推理）与分层评测框架（30 条用例 5 个能力层级、
   9 项指标、重复实验取方差、结果自动落盘）。
2. **方法层**：指出并修正了初版评测的四处会导致结论失真的缺陷——
   工具调用只算召回（退化解可拿满分）、根因判定用 `split()[0]` 在中文上截断、
   拒答判定只要出现"正常"二字即算对、以及测试集与环境不自洽。
   这些缺陷若不复现，任何实验结论都不可信。
3. **结论层**：用修复后的框架证伪了"证据校验"这一设想，并给出失败机制分析
   （校验本身也是 LLM 调用、判定精度不足；"拦截重写"代价不对称），
   提出 5 条改进路径。

**核心话术**：本项目的主要贡献不是"做出了一个能用的 Agent"，
而是"建立了可复现的评测方法，并用它证伪了一个看似合理的改进设想"。
后者在研究方法上是更有价值的产出。

### Q2：L5 拒答正确率只有 44.4%，是不是做得不好？

承认，并且给出**机制性解释**——这比辩解更有说服力。

实测发现幻觉是**系统性的、而非随机的**。逐条数据显示：

| 问法 | 根因正确率 | 幻觉率 |
| :--- | :--- | :--- |
| "gateway-service 有没有**缓存穿透**问题？" | 0/3 | 3/3 |
| "gateway-service 有没有**内存泄漏**？" | 0/3 | 3/3 |
| "gateway-service 有没有**连接池**问题？" | 3/3 | 0/3 |
| "gateway-service 现在运行**正常**吗？" | 3/3 | 0/3 |
| "帮我查一下 **payment-service** 的监控" | 1/3 | 0/3 |

规律是：**用户用具体故障名提问时（"有没有 X"），模型会顺着问法编造 X**；
而中性提问（"正常吗"）或询问不存在的服务时，反而不编。
这属于**确认偏差 / 诱导性提问效应**。

结论：该偏差无法通过"证据校验"这类事后审查消除，需要从提问框架或
工具调用前置约束入手。这已列为最优先的后续工作。

### Q3：每层只有 6 条用例，样本量够吗？

**这是真实的弱点，建议直接承认**：样本量偏小，分层结论的稳定性不足。
证据：同一配置跨不同轮次的运行中，L2 根因准确率在 72.2%-75.0% 之间波动、
基线 L3 曾在 77.8%-88.9% 之间波动，波动幅度接近标准差。

说明：30 条用例足以支撑**总体层面**的结论（总体指标标准差仅 ±1.9-3.8pp），
但**分层指标**的置信度有限。后续应将每层扩至 12-15 条。

### Q4：你的数据是模拟的，结论对真实环境有效吗？

不要回避，转化为方法论声明：

> 真实生产故障数据涉及企业敏感信息且难以复现。本文构建确定性仿真环境，
> 用于在可控条件下对比不同策略的**相对性能**差异，而非宣称绝对性能指标。
> 仿真环境不含随机数，因此实验间的差异可归因于模型而非数据。

可补充：`selfcheck.py` 的 23 项断言保证"标准答案与仿真数据自洽"，
任何人无需 API Key 即可验证这一点。

### Q5：为什么用 LangChain 的 `create_agent` 而不自己实现 ReAct？

如实说明：本项目关注点在于**评测与验证方法**，而非 Agent 编排机制的重新发明。
`create_agent` 提供标准的 ReAct 循环，使实验聚焦于可对比的变量
（有无 RAG、有无证据校验）。自建编排被列为后续工作
（用 LangGraph 显式状态机以约束最大轮数，缓解无效工具调用问题）。

### Q6：工具调用精确率只有 76.7%，是什么原因？

有数据支撑的诚实回答：召回率 100%、精确率 76.7%，说明 Agent
**需要的工具都能调到，但会多调**。实测平均调用 3.8 次、最多 9 次，
典型表现是对不存在的服务重复调用同一个监控工具 3 次。
根因是 ReAct 自由循环缺乏停止条件约束，已列为后续工作。

### Q7：现场演示时如果跑不出来怎么办？

**务必提前准备**：

- 演示前先跑 `python selfcheck.py`（不耗额度，约 30 秒），证明环境与判分逻辑正常；
- 演示用问题选 L1/L4 类：L1 约 2-3 秒返回，L4 约 4-7 秒；
- **避免用 L3 类做现场演示**（单次可达 40 秒，观感差且易超时）；
- 若网络或 API 异常，直接展示 `results/report_latest.md` 与
  `results/diagnostics.md` 作为已完成的实验证据。
