# 评测指标与判分口径说明

本文档说明 `evalframework.py` 中每个指标的**含义、计算方式与已知边界**。
论文的"实验方法"章节可直接引用，也便于答辩时回答"你怎么判对错的"。

## 一、为什么要重做评测

初版评测存在三处会导致结论失真的问题，此处如实记录，作为方法改进的依据。

### 问题 1：工具调用只算召回，退化解可拿满分

初版：

```python
tool_hits = sum(1 for t in case["expected_tools"] if t in called_tools)
tool_score = tool_hits / len(case["expected_tools"])
```

这是纯召回率。后果：**一个对每个问题都调用全部工具的 Agent，准确率恒为 100%**。
本项目实测中，Agent 在"查询不存在的服务"时调用了 3 次同一个监控工具，
在"服务是否正常"这类简单问题上调用了 7 次工具——初版指标全部判为满分。

**修正**：改用精确率/召回率/F1，多调与漏调同时受罚。

### 问题 2：根因判定用 `split()[0]`，中文上会截断

初版：

```python
key = case["ground_truth"].split()[0]
root_correct = key in final_answer
```

中文短语内部没有空格，`split()[0]` 会取到标点前的整段文字。例如标准答案
`"回滚版本，调大 max_connections"` 取到 `"回滚版本，调大"`，
一个正确回答"回滚到 v2.1.0 并调整 max_connections"会被判错。

**修正**：改为短语组匹配（`must_roots`），每个元素是一组同义表达，
任一命中即算该组命中，**全部组命中**才算根因正确。

### 问题 3：拒答判定只要出现"正常"二字即算对

初版：

```python
deny_phrases = [..., "正常", "没有问题", ...]
if any(dp in final_answer for dp in deny_phrases):
    root_correct = True
```

后果：`"CPU 指标正常，但日志中有大量 ERROR，响应时间已劣化到 3.2s"`
这种**描述真实故障**的回答会被判为"正确拒答"。
而拒答能力恰恰是该项目的核心创新点，这个判定失效会让相关数字完全不可信。

**修正**：见下文第三节。

## 二、指标定义

| 指标 | 计算方式 | 说明 |
| :--- | :--- | :--- |
| 工具精确率 P | 去重后调用的工具中，属于期望集合的比例 | 惩罚多调 |
| 工具召回率 R | 期望工具中被调用的比例 | 惩罚漏调 |
| 工具 F1 | `2PR/(P+R)` | 综合指标 |
| 证据命中率 | 命中的证据短语组数 / 总组数 | 短语组内任一表达命中即算该组命中 |
| 根因准确率 | `must_roots` 全部命中 **且** 未断言任何 `forbidden_roots` | 末条用于捕捉"主根因正确但夹带幻觉" |
| 拒答正确率 | L5 专有，见第三节 | |
| 幻觉根因率 | 断言了工具数据不支持的根因的比例 | 越低越好 |
| 触发重答率 | 证据校验判定为编造并触发重答的比例 | 反映校验环节的介入频率 |
| 纯 Agent 耗时 | 总耗时 − 校验耗时 | 扣除校验开销后的模型推理时间 |
| 校验耗时 | 证据校验环节实际耗时 | 用于量化校验的性能代价 |

### 关于重复实验

LLM 输出具有随机性，单次运行的均值本身就是一个噪声点。
因此所有指标按 **"每个重复先汇总、再跨重复取均值 ± 标准差"** 计算，
报告中统一以 `均值 ± 标准差` 呈现。

## 三、拒答（L5）判定口径

拒答类用例分三种：

| kind | 含义 | 判定 |
| :--- | :--- | :--- |
| `lookup` | 服务健康，应回答"正常" | 必须命中 `must_roots`，且未断言任何根因 |
| `deny` | 该服务确实无此问题 | 必须明确否认，且未断言任何根因 |
| `unknown` | 服务不存在 | 必须如实说明查不到，且未编造指标或根因 |

判定公式：

```
拒答正确 = 存在明确否认表述  AND  未断言具体故障根因
```

### 关键难点：区分"否认"与"提及"

朴素的 `关键词是否出现` 无法工作，因为：

- `"没有发现内存泄漏"` —— 含"内存泄漏"，但这是**正确拒答**
- `"存在内存泄漏"` —— 含"内存泄漏"，这是**幻觉**

因此实现了基于**子句级语气分析**的断言检测，需同时满足三个条件才认定为"断言"：

1. **非否定**：根因词之前不能有否定词（`没有 / 未发现 / 不存在 / …`）
2. **非比较**：分句中不能有对比性标记（`典型 / 相比 / 对比 / 例如 / …`）
3. **非弱化**：分句中不能有推测性标记（`不排除 / 大概率 / 或许 / …`）→ 命中也算断言

此外，含转折词（`但 / 然而 / 不过 / …`）的句子会先被拆成分句再判断，
否则 `"CPU 正常，但日志有大量错误"` 会被误判为整体正常。

### 该口径的已知边界（须在论文中如实说明）

1. **规则判分，非语义理解**。上述规则基于词表与子句切分，本质是启发式。
   由于规则刻意选择"宁可多报幻觉也不少报"的严格方向，**可能高估幻觉率**；
   反之若表述超出词表覆盖，也可能漏报。
2. **词表维护成本**。新增故障类型时需同步扩充 `CONCRETE_ROOT_MARKERS` 等词表。
3. **未采用 LLM 作为裁判**。选择规则判分是为了保证完全确定性、零额外 API 成本
   且可离线自检。若追求更高判定质量，可替换为 LLM-as-a-Judge，
   但需注意引入裁判模型自身的偏差，并需报告裁判与人工标注的一致性。

### 自检机制

`selfcheck.py` 用 53 项断言覆盖上述全部规则，其中包括**对抗性样例**：

- 完美回答 → 必须判对
- 主根因正确但夹带幻觉根因 → 必须判错
- 含"正常/没有"但实质断言根因 → 必须判错
- 正确拒答但含对比性提及（如引用历史故障做对照）→ 必须判对
- 推测性根因断言（"不排除存在…的可能"）→ 必须判错

该脚本**不调用任何 LLM API**，任何人 clone 后可直接运行，
用于确认"标准答案与仿真数据自洽、判分逻辑符合预期"。

## 四、仿真环境的可复现性

`simulator.py` 不含随机数，同一输入永远返回同一输出。
唯一的随机性来源是 LLM 本身，因此实验间的差异可归因于模型而非数据。

四个服务的故障状态刻意互不相同：

| 服务 | 状态 | 用途 |
| :--- | :--- | :--- |
| order-service | 连接池耗尽 | 主故障场景，需交叉推理 |
| product-service | 缓存穿透 | 内存正常但 CPU 与响应时间劣化 |
| user-service | 内存泄漏 | 需读跨天趋势才能定性 |
| gateway-service | **完全健康** | 拒答测试的前提；若所有服务都有故障，就无法测"该说正常时能否说正常" |

### 为什么需要 gateway-service

初版设计中所有服务都带故障，导致"某服务现在正常吗"这类问题没有唯一正确答案，
拒答能力无法被真实测量。增设一个完全健康的服务后，
`lookup` 类用例才有了确定的判定基准。

### 为什么使用仿真数据

真实生产故障数据涉及企业敏感信息且难以复现。本文构建确定性仿真环境，
目的是在可控条件下对比不同检索与编排策略的**相对性能**差异，
而非宣称绝对性能指标。这一取舍须在论文中明确声明。
