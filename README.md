# 智能运维 Agent

基于大模型和 RAG 的自动化故障排查系统。用户输入一句自然语言的运维问题，Agent 自动查监控、查日志、查发布记录、翻历史故障报告，输出带证据链的根因分析。

## 项目背景

传统运维排查需要人工依次查看监控面板、搜索日志、核对发布记录、翻找历史故障报告，耗时长且容易遗漏。本项目把这套流程交给 AI Agent 自动完成，并重点做了两件事：

1. **构建可信的评测基础设施**——确定性仿真运维环境 + 分层测试集 + 可复现评测框架；
2. **用该框架验证"证据校验"这一改进设想是否有效**——实测结论是**无效**，详见下节。

## 核心结论（重要）

本项目最初设想通过"证据校验"环节抑制模型编造故障根因。经 30 条分层用例、3 次重复的对照实验，**该设想未获支持**：

| 指标 | 无证据校验（基线） | 含证据校验 | 变化 |
| :--- | :--- | :--- | :--- |
| 根因定位准确率 | 78.9 ± 3.8% | 71.1 ± 1.9% | **−7.8 pp** |
| 幻觉根因率（越低越好） | 10.0 ± 0.0% | 17.8 ± 1.9% | **+7.8 pp（变差）** |
| 拒答正确率（L5） | 44.4 ± 9.6% | 38.9 ± 9.6% | −5.5 pp |

原因分析：校验环节本身也是一次 LLM 调用，判定精度不足；而"拦截并重写"的代价不对称——把正确结论改写成"证据不足"是确定性损失，它本应防止的幻觉却只是概率性收益。基线本身的幻觉率已较低（10.0%），校验在解决一个并不严重的问题。

**完整分析见 [`docs/实验结果与结论.md`](docs/实验结果与结论.md)。** 该结论以负面结果形式如实记录，包含失败机制分析与后续改进方向。

## 核心功能

- 自动调用监控工具查询 CPU、内存、响应时间（**返回时间序列**，需读趋势而非单值）
- 自动搜索服务日志中的错误信息
- 自动查询服务的发布记录
- 基于 RAG 检索历史故障报告，引用历史经验
- 输出带证据链的结构化根因分析报告
- 提供 Web 界面，支持浏览器交互演示
- **不消耗 API 额度即可运行的自检脚本**，用于验证仿真环境与判分逻辑
- 可复现的分层评测框架，支持多配置对照、重复实验取方差、结果自动落盘

## 技术栈

- 大模型：DeepSeek（deepseek-chat）
- Agent 框架：LangChain（`create_agent`，内置 ReAct 循环）
- 向量数据库：Chroma
- Embedding 模型：BAAI/bge-small-zh-v1.5（本地运行，免费）
- 后端：FastAPI + Uvicorn
- 前端：原生 HTML + JavaScript

> 说明：`langgraph` 虽在依赖中（LangChain Agent 的传递依赖），但本项目**未直接使用**其显式状态机编排能力，架构为 ReAct 自由循环。这一点已在"后续可扩展方向"中列为待做项，避免材料与实现不符。

## 架构说明

### Agent 工作流（ReAct）

```
用户提问
   ↓
模型思考：需要哪些信息？
   ↓
调用工具（可多轮）：
  ├── query_prometheus      → 查监控（时间序列）
  ├── search_logs           → 查日志
  ├── get_deployment_record → 查发布记录
  └── search_fault_reports  → 查历史故障报告（RAG）
   ↓
观察结果 → 继续思考 → 直到信息足够
   ↓
生成诊断报告
   ↓
【证据校验】根因是否在工具返回数据中有依据？
   ├── 无依据 → 判定为编造，要求基于证据重答
   └── 有依据 → 直接输出
```

### 证据校验（已实测，未达预期）

证据校验针对的失败模式是：Agent 在查完数据后给出数据并不支持的"具体根因"。
实现方式是：由审核模型检查报告中的根因能否由工具返回数据推出，若不能则要求重答。

实测表明该环节**判定过于激进**（30 条用例触发 13 次重答，连"内存使用率是多少"
这类纯查询也会触发），且重答会把证据充分的正确诊断改写成"证据不足"，
最终导致准确率下降。该环节保留在代码中作为被验证的负面对照，
`eval_v3.py --configs basic/verified` 即为该消融实验的开关。

### 1. 环境要求

- Python 3.10+
- 一个 DeepSeek API Key（[platform.deepseek.com](https://platform.deepseek.com/)）

### 2. 安装依赖

```bash
pip install -r requirements.txt
```

### 3. 配置 API Key

在项目根目录创建 `.env` 文件：

```
OPENAI_API_KEY=你的DeepSeekKey
OPENAI_API_BASE=https://api.deepseek.com/v1
OPENAI_MODEL=deepseek-chat
```

> `.env` 已在 `.gitignore` 中，不会被提交。请勿把 API Key 写进代码或截图。

### 4. 构建知识库

```bash
# 设置 HuggingFace 国内镜像（加速 Embedding 模型下载）
set HF_ENDPOINT=https://hf-mirror.com

python rag_setup.py
```

### 5. 启动 Web 服务

```bash
python -m uvicorn main:app --reload
```

打开浏览器访问 `http://127.0.0.1:8000`。

### 6. 命令行运行（可选）

```bash
python agent_v1.py   # 无 RAG 的对照组
python agent_v2.py   # 含 RAG，无证据校验
python agent_v3.py   # 含证据校验（本方案）
```

## 评测

### 先跑自检（不消耗 API 额度）

```bash
python selfcheck.py
```

自检覆盖三类内容，共 56 项断言：

1. **仿真环境自洽性**（23 项）——`simulator.py` 返回的数据是否与测试集标注一致（例如 order-service 确实有连接池报错、gateway-service 确实全程健康）。
2. **测试集结构合法性**（5 项）——用例 ID 唯一、覆盖 L1-L5、每条都有可判分的断言、L5 都标注了 `kind`。
3. **判分逻辑对抗性测试**（28 项）——用"完美回答 / 夹带幻觉的回答 / 正确拒答 / 含对比性提及的正确拒答 / 推测性断言"等多类样例检验判分是否会误判。

> 这一步是实验可复现性的一部分：任何人 clone 本仓库后**无需 API Key** 即可确认"标准答案与仿真数据是自洽的、判分逻辑符合预期"。

### 正式评测

```bash
# 完整消融实验：基线与本方案各跑 3 次
python eval_v3.py --configs both --repeats 3 --warmup 1 --workers 8

# 只跑基线（等价于旧的 eval_v2.py）
python eval_v3.py --configs basic --repeats 3

# 只跑某一层
python eval_v3.py --configs both --level L3,L5 --repeats 3

# 小样本快速验证链路（避免一上来就大量调用）
python eval_v3.py --configs both --limit 4 --repeats 1
```

> **注意耗时**：复杂用例（L3/L4）单次会话需 5-8 轮 LLM 往返，实测可达 40 秒。
> 30 条用例 × 2 配置 × 3 重复串行执行需 1.5-2 小时，
> 因此评测框架支持 `--workers` 并发（默认 4，建议 8）。

结果会同时输出到终端，并落盘到 `results/`：

- `raw_<时间戳>.json` / `.csv`：每条用例的明细（工具调用序列、各指标、耗时拆分、回答摘要）
- `report_<时间戳>.md`：分层指标表 + 消融对比表，可直接引用
- `report_latest.md`：最新一次报告的副本
- `diagnostics.md`：**逐条用例的工具调用序列与回答摘要**，用于核查指标异常

### 测试集设计

`testset.json` 共 30 条用例，按能力分为 5 层：

| 层级 | 能力 | 条数 | 示例 |
| :--- | :--- | :--- | :--- |
| L1 | 单工具事实查询 | 6 | "order-service 昨晚的 CPU 使用率是多少？" |
| L2 | 多工具联合推理 | 6 | "order-service 的监控数据怎么样？顺便看看昨晚发版了吗？" |
| L3 | 根因定位 | 6 | "order-service 昨晚为什么响应变慢？" |
| L4 | 历史经验迁移 | 6 | "历史上有没有类似的连接池故障？当时是怎么解决的？" |
| L5 | 边界与拒答 | 6 | "gateway-service 有没有内存泄漏？"（实际没有，考察是否编造） |

每条用例标注：

- `expected_tools`：期望调用的工具集合
- `valid_tool_sets`：**等价工具集**。某些问题可通过不同证据路径回答
  （如"有无内存泄漏"既看监控也看日志），命中任一等价集即视为最优，
  避免把另一种正确答案误判为"多调工具"
- `evidence_keywords`：回答中应出现的证据（支持 `同义词|同义词` 的短语组写法）
- `must_roots`：根因必须命中的短语组（**全部组命中**才算对）
- `forbidden_roots`：不应被**断言**的根因（用于捕捉"主根因正确但夹带幻觉"）
- L5 额外有 `kind`：`deny`（该服务确实无此问题）/ `lookup`（服务健康）/ `unknown`（服务不存在）

### 评测指标

| 指标 | 说明 |
| :--- | :--- |
| 工具精确率 / 召回率 / F1 | 同时惩罚"漏调"和"多调"。只算召回会让"每题都调全部工具"的退化解拿满分 |
| 证据命中率 | 回答中命中了多少组期望证据 |
| 根因准确率 | 根因短语组全部命中，且未断言任何禁用根因 |
| 拒答正确率 | L5 专有：必须明确否认该问题且未断言具体根因 |
| 幻觉根因率 | 断言了工具数据不支持的根因的比例，越低越好 |
| 触发重答率 | 证据校验判定为编造并触发重答的比例 |
| 耗时拆分 | 纯 Agent 耗时与校验耗时分开统计 |

**所有指标按"每个重复先汇总、再跨重复取均值 ± 标准差"计算**，因为 LLM 输出有随机性，单次运行的均值本身就是一个噪声点。

### 评测结果

最新一次完整评测（30 用例 × 2 配置 × 3 重复）的结果见 **`results/report_latest.md`**，
包含分层指标表与消融对比表。完整分析与失败机制见 **[`docs/实验结果与结论.md`](docs/实验结果与结论.md)**。

核心结论概述：

| 层级 | 能力 | 根因准确率（基线） | 根因准确率（校验） |
| :--- | :--- | :--- | :--- |
| L1 | 单工具事实查询 | 100.0% | 100.0% |
| L2 | 多工具联合推理 | 72.2% | 66.7% |
| L3 | 根因定位 | 77.8% | 50.0% |
| L4 | 历史经验迁移 | 100.0% | 100.0% |
| L5 | 边界与拒答 | 44.4% | 38.9% |
| **总体** | — | **78.9%** | **71.1%** |

指标口径为"均值 ± 标准差"，跨重复次数统计。**请以仓库中实际生成的文件为准，不要手工誊抄数字**——这样可以避免文档与代码脱节。

两个值得注意的发现：

- **基线架构本身有效**：L4（历史经验迁移）达 100%，说明 RAG 确实让 Agent 能答出"连接未释放""需用 try-with-resources"这类只存在于知识库中的细节。
- **L5 是真正的短板**：拒答正确率仅 44.4%，模型在服务健康时容易编造根因——这才是值得投入优化的方向。
- **工具调用存在浪费**：工具 F1 仅 83.1%（召回 100%、精确率 76.7%），说明 Agent 把需要的工具都调到了，但常重复调用或调用无关工具（如对不存在的服务调用 3 次监控）。

## 仿真环境说明

`simulator.py` 是一个**确定性**（无随机数）的仿真运维环境，**四个**服务的故障状态刻意各不相同：

| 服务 | 状态 | 说明 |
| :--- | :--- | :--- |
| order-service | 故障 | 2024-01-15 发布 v2.3.1 后连接池耗尽，CPU 与响应时间同步劣化，**内存正常** |
| product-service | 故障 | 2024-02-15 凌晨缓存穿透，Cache miss 95%，CPU 与响应时间劣化，**内存正常** |
| user-service | 故障 | 03-18 至 03-20 内存从 40% 持续爬升到 89% 并 OOM，属内存泄漏特征 |
| gateway-service | **健康** | 四项指标全程在基线附近，日志只有 INFO，用于拒答测试 |

四个设计要点：

1. **必须存在一个完全健康的服务**。若所有服务都带故障，"某服务现在正常吗"就没有唯一正确答案，拒答能力无法被真实测量——这是初版设计的缺陷。
2. **指标是时间序列**，不是单值快照。Agent 必须读趋势才能区分"内存高"和"内存泄漏"（后者是跨天持续爬升，单看一个 85% 无法定性）。
3. **证据需交叉推理**。order-service 的 CPU 与响应时间同步劣化、内存正常，单看一个工具读不出根因，必须结合日志与发布记录；且发布记录里刻意放了与故障无关的干扰版本 v2.2.0。
4. **日志含干扰项**。每个故障服务都混有 INFO 级正常日志，检索时会产生噪声。

> **为什么要用仿真数据**：真实生产故障数据涉及企业敏感信息且难以复现。本文构建确定性仿真环境，目的是在可控条件下对比不同检索与编排策略的**相对性能**差异，而非宣称绝对性能指标。这一取舍已在 `docs/实验结果与结论.md` 的方法局限一节中声明。

## 示例输出

输入：

> 帮我看看 order-service 昨晚为什么响应变慢了

输出（节选）：

> **结论**：order-service 昨晚变慢的根本原因是 v2.3.1 的连接池配置变更导致数据库连接池耗尽。
>
> **证据链**：
> - 22:50 发布 v2.3.1，变更内容为"优化连接池配置"
> - 23:00-01:00 响应时间从 0.2s 升至 3.2s，CPU 从 14% 冲到 95%，内存平稳在 60%
> - 23:12 日志报错 `Connection pool exhausted max=50 active=50 waiting=37`
>
> **历史故障对照**：这与 2024-01-10 的故障报告几乎一致。上次同样是 max_connections 配置过小，当时从 50 调整到 200 解决。本次属重复踩坑，建议纳入发布 checklist 强制卡点。

## 后续可扩展方向

按优先级排列，前两项基于实测发现的真实短板：

- **攻克 L5 拒答能力**（当前最大短板，拒答正确率仅 44.4%）。实测显示模型在服务健康时
  倾向于编造一个看起来专业的根因。可行方向：把"拦截重写"改为"并列出证据缺口"，
  或仅在"指标正常却给出故障根因"这种低置信场景触发校验（而非对所有回答校验）
- **检索增强**：对比纯向量 / BM25 / 混合检索（RRF），做切分参数与 `k` 的消融实验
- **知识库扩容**：当前仅 3 篇故障报告，扩到 20-30 篇后检索质量才成为真问题
- **查询改写**：把"响应变慢"改写成"连接池耗尽 响应时间飙升 CPU 升高"再检索
- **减少无效工具调用**：实测 Agent 常重复调用同一工具（如对不存在的服务调用 3 次监控），
  工具精确率仅 76.7%，可通过约束停止条件或引入工具预算改善
- **多 Agent 协作**：诊断 Agent + 证据校验 Agent + 报告 Agent
- **用 LangGraph 显式编排**：当前的 ReAct 自由循环难以约束轮数，
  显式状态机可支持"检索不相关时重试"与最大轮数控制
- **流式输出**：用 SSE 把推理链实时推送到前端
- **对接真实数据源**：Prometheus、ELK、发布系统 API

详见 `docs/毕业设计升级方案.md`。
